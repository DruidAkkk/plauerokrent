# Спайк «идём / не идём» — отчёт

Дата: 2026-10-12. Среда: Windows 11, Python 3.14 (venv `.venv`), `cryptography`, `curl_cffi 0.16.3`, `steampy 1.2`.
Весь сетевой код гоняет **реальный адаптер** `rentbot/adapters/playerok.py`, а не отдельную копию.

## Итог: ИДЁМ по Playerok. Steam — идём, но ротация остаётся ручным прототипом (как и планировалось).

## 1. Playerok — ✅ ЗАРАБОТАЛО (подтверждено вживую)

Запуск без токена, доказывает весь сетевой путь:
```
python spike/playerok_check.py --selftest
```
Результат:
- **Cloudflare пройден** — `curl_cffi` с `impersonate` отдаёт `GET / → 200` без челленджа.
  Проверены `chrome, chrome124, chrome120, chrome116, safari17_0` — все 200. Это не обход
  защиты, а корректный TLS-отпечаток; CAPTCHA/эвазия не нужны.
- **Публичный каталог** `POST /v1/catalog/items` → 200, структура `{items, endCursor, hasNextPage}`
  как в брифе; у item есть `price, dealsCounter, seller, game, category, priority` и т.д.
- **GraphQL принимает обычные тексты операций** — persisted-хэши НЕ обязательны (важное упрощение).
  Тексты `viewer / deals / chats / chatMessages / createChatMessage` сняты из JS-бандлов фронта
  и провалидированы против живой схемы (все проходят валидацию; падают только на auth, не на синтаксисе).
- **Обязателен заголовок** `apollo-require-preflight: true` (без него 400 CSRF) — вшит в адаптер.

Auth-путь тоже проверен (с заведомо неверным токеном): адаптер поднимает сессию, ставит
cookie `token`, проходит Cloudflare, выполняет `viewer` и чисто сообщает «токен невалиден».
То есть **не хватает только живого токена** — всё остальное работает.

### Что осталось на тебя (10 секунд утром)
1. DevTools → Application → Cookies → `playerok.com` → значение `token`.
2. ```
   set PLAYEROK_TOKEN=...            # (PowerShell: $env:PLAYEROK_TOKEN="...")
   python spike/playerok_check.py    # увидишь свои чаты/сделки и id чатов
   ```
3. Взять `id` своего чата из вывода и отправить тест:
   ```
   set PLAYEROK_TEST_CHAT_ID=<id из списка>
   python spike/playerok_check.py --send
   ```
   Критерий успеха (`[verify] сообщение НАЙДЕНО`) проверяется автоматически.

### Не до конца закрыто
- `set_lot_active` (скрыть/показать лот): мутации найдены (`publishItem` требует
  `itemId + priorityStatuses + transactionProviderId`; `removeItem`), но точные значения
  снимаются только с **живого лота продавца**. Для режима «только аренда» некритично
  (лот можно держать видимым) — поэтому пока явный `NotImplementedError` с пояснением.
- WebSocket (`wss://ws.playerok.com/graphql`) не поднимал — в MVP основной путь страховочный
  опрос `deals`/`chats`; `run()` уже реализует опрос с антибан-паузами и ретраем по Cloudflare.
- Какая `direction` у входящих сделок продавца (`IN`/`OUT`) — увидим на живом токене; опрос
  сейчас не фильтрует по direction, фильтр «оплачено» по статусу `*PAID*`.

## 2. Steam — ✅ безопасная часть работает; ⚠️ ротация пароля — ручной прототип (осознанно)

Запуск без секретов:
```
python spike/steam_check.py --selftest
```
Результат:
- **Парсинг maFile** (shared_secret, identity_secret, account_name, steamid) — OK.
- **Guard-код** из `rentbot/steam/guard.py` **совпадает** с эталоном `steampy.guard` (две
  независимые реализации TOTP дают один код). Guard готов.
- **Логин через прокси** (`--login`, steampy) реализован как **чтение**: поднять сессию и
  подтвердить `is_session_alive()`. Тестируется, когда дашь maFile + пароль + прокси в env.

### Почему смена пароля + деавторизация НЕ выполнялись автономно ночью
Это сознательное решение, а не затык:
1. **Нет входных данных** — по твоему же правилу секреты только из env, в репозитории их нет;
   без maFile и пароля логин/подтверждение/смена физически не запускаются.
2. **Единственная необратимая операция проекта.** Сбой в середине web-флоу смены пароля на
   `help.steampowered.com` = потеря доступа к аккаунту. Твой бриф прямо говорит: это
   *«прототип недели 1 на собственных аккаунтах»* — значит, с мобильным аутентификатором в руке.
3. **Нечего «гонять до победы» вслепую** — автоматический reset-флоу проверяется только против
   живого аккаунта с подтверждением в приложении. Это human-in-the-loop по определению.

Поэтому `rotate_credentials` остаётся в `rentbot/steam/backend.py` как каркас и запускается
осознанно человеком. Когда будешь за компом с тестовым аккаунтом — садимся и доводим его вместе
(путь A: steampy; при нестабильности — путь B: Node-сайдкар, как в брифе).
